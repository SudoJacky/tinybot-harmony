# App 内性能诊断

在“设置 → 关于 Tinybot”连续点击版本号 7 次，相邻点击间隔不超过 2 秒，输入本工程约定的固定开发者密码。开启后，“设置”显示“开发者模式”入口。这只是本地功能入口，不是身份认证或权限边界；不会提升系统权限。密码不写入日志、Preferences 或备份。关闭模式后需要重新解锁；连续输错 5 次暂停尝试 30 秒，关闭密码弹层后清空输入。

首次开启自动开始诊断采集，包含性能数据与运行日志。开发者模式开关单独保存在本机 `tinybot-developer` Preferences，应用进程重启后保留入口，但不会自动开始采集。关闭采集会释放采样定时器、displaySync、系统事件订阅和 CPU profiler。关闭采集后 Debug/Info 仅检查状态和等级；没有资源探测、周期落盘、逐帧回调、日志拼接或缓冲写入。Warn/Error 仍通过统一脱敏后输出到系统 HiLog，但不会进入诊断缓冲或滚动文件。

## 复现场景

1. 开始采集，按需选择“详细事件时间线”。默认开启；关闭时仍汇总所有关键路径耗时，保留慢操作、资源和系统事件。
2. 点击“记录场景标记”，返回聊天，复现长回答、历史滚动、工具调用或 Web 预览。再次标记可区分场景边界。
3. 回到开发者页，查看全程统计与最近慢操作。“停止并导出”生成 JSON 诊断包，由系统文件选择器保存；也可通过系统分享发送。
4. 需要函数级分析时，单独启动最多 30 秒的 ArkTS CPU 采样，再到聊天复现。超时、进入后台或停止采集都会结束 profiler。CPU Profile 单独导出，可使用支持 Chrome CPU Profile 的工具检查。
5. “清除诊断数据”停止采集，删除两份内部日志、缓存诊断包和 CPU Profile，清空当前内存统计。用户已经导出或分享的副本由用户管理。

## 指标和时间线

| 分类 | 实际记录 |
| --- | --- |
| Markdown | 全量源字符数、变更起点和块数；增量解析、行内解析、Span 数、代码高亮及表格宽度计算耗时 |
| 渲染 | 活跃文档/分组数；分组更新、分批挂载耗时和进度；可见性、淡入时钟次数 |
| 布局/滚动 | 分组实测宽高、消息高度变化、自动跟随触发；尺寸单位为 vp |
| 网络 | 请求耗时、首段正文延迟、接收字节、正文增量数/字符数、协议解码解析和状态投影的耗时；HTTP 状态、失败和取消标记 |
| 工具 | 操作 ID、轮次、参数/结果字符数、执行耗时、失败/取消状态；不包含参数或结果正文 |
| 会话 | 上下文估算、会话发布、ViewModel 投影、存盘前序列化、文件写入（含 fsync）的耗时 |
| Web | 实例创建、释放、活动数量、代次、loadData 调用耗时和 ready 事件 |
| 资源 | HiDebug 当前应用进程 PSS+SwapPss、RSS、VSS、私有/共享脏页；UI VM 堆总量/已用量/数组大小；进程 CPU 和最多 32 个 CPU 占用最高的线程 |
| 主线程 | 250 ms 周期定时器的迟到时间；可选 displaySync 回调间隔与目标 Vsync 周期 |
| 系统 | HiAppEvent MAIN_THREAD_JANK、APP_FREEZE、APP_CRASH、RESOURCE_OVERLIMIT 的固定名称及允许的数值字段；到达时间与系统发生时间分别保留 |

字符数使用 ArkTS `string.length`（UTF-16 码元），网络字节数另行统计。HiDebug CPU Profile 保存在 application filesDir，与模块诊断日志目录不同。

所有耗时使用系统启动单调时钟，不随校时变化。资源默认前台约每秒一次，慢 IPC 和 smaps 采集放在 taskpool，UI VM 堆在 UI VM 读取。异步结果检查采集代次和前后台状态，避免旧任务污染下一次采集。进入后台停止主动定时器与帧回调，保留已经在运行的应用路径埋点及系统事件订阅。

`diagnostics.resourceProbe` 包含工作线程排队、探测和结果返回耗时；采样任务本身的资源消耗也包含在被测进程中。CPU API 使用平台原始口径乘 100；不与外部工具不同分母的 CPU 数值直接作等同比较。VM 仅 UI VM，进程内存不包含独立 Web 进程。采集器不把失败样本当零值补入统计；诊断页与导出包中的 `diagnostics.error` 标明来源和系统错误码（1=偏好存储，2=取消系统订阅，3=资源探测，4=帧回调，5=订阅系统事件，6=日志文件，7=CPU profiler）。停止采集后发生的错误还会写入导出元数据 `diagnosticError`。

“逐帧回调采样”默认关闭。开启会主动请求 Vsync，增加功耗并改变被测条件。回调间隔和定时器迟到都不能当作官方掉帧率；它们不是渲染完成时间。单次资源采样也可能漏掉瞬时峰值。正式帧率、native/GPU 调用栈、调度和多进程内存仍需 DevEco Profiler、HiTrace 或 SmartPerf。

## 容量、导出与开销

`Diagnostics.ets` 不依赖原生平台，性能与运行日志使用同一个单例；`DiagnosticLog.ets` 统一处理名称、字段和异常脱敏；仅 `NativeDiagnosticLog.ets` 可以写 HiLog；`DeveloperDiagnostics.ets` 负责本机开关、生命周期、系统采样与导出；`PerformanceProbe.ets` 在工作线程收集慢资源数据。性能埋点仅传固定事件名与数值；运行日志只保留允许的结构化字段，不导出密钥、URL、正文、工具参数、文件路径或系统堆栈文本。CPU Profile 是单独按需生成的函数/源码路径采样，不包含堆快照。

内存事件使用最多 12000 条的环形缓冲，全程聚合统计独立保留，最多 128 类指标。覆盖和省略计数明确展示。分位数是固定直方图的上界，均值/最大值/次数为实际采集值。详细模式每次埋点会读时钟、更新统计并写入环形缓冲，会产生分配，不能当作无开销性能基线。

布局回调总数独立聚合，只有宽高改变时才写布局明细，避免位置变化或相同尺寸回调淹没时间线。Markdown 源长度也单独汇总，即使早期解析事件被环形覆盖，仍能看到本次最大输入规模。

每 5 秒异步批量追加 JSONL，每份日志达到约 4 MiB 时轮转，保留当前和前一份（单批数据可使文件略超阈值）。首次写入新采集时也会轮转。文件写入处理短写，失败通过诊断状态报告。进程异常退出可能丢失最后约 5 秒；这不是同步的崩溃日志保证。重新启动后可以导出上一进程已经写入的日志。不会在正常模式自动上传或持续生成日志。

schema 2 诊断包含版本、指标口径、全程统计、性能事件、独立运行日志、两份 JSONL 和联合 `traceEvents`，可在支持 Chrome Trace JSON 的分析器中查看。时间线使用逻辑进程/线程分组，不冒充真实内核 TID；真实 CPU 线程 ID 在资源事件的 operationId 中。网络请求和渲染组件各有本地数值 ID，通过时间对齐，不宣称具有精确的请求到消息渲染映射。导出时先停止采集，避免把序列化大包的耗时混入业务统计。

本地回归入口为 `node scripts/test-developer-diagnostics.cjs`，同时包含在 `scripts/test.ps1` 中。覆盖关闭路径、容量/分位数、解锁、失效异步结果、采样生命周期、可选帧回调、CPU profiler 停止、批量落盘、短写、轮转、失败重试、清除与导出。


## 统一运行日志接口

业务统一使用 `model/Diagnostics` 导出的 `Diagnostics`。`log(level, module, event, fields?, error?)` 与 `begin/end`、`measure`、`event` 共用采集状态、单调时钟和序号。会话的依赖注入接口 `reportError/reportMemory/reportResources` 只转交该入口，不再自行格式化或输出日志；浏览器回调也改为结构化事件。

```typescript
if (Diagnostics.acceptsLog('debug')) {
  Diagnostics.log('debug', 'web', 'load_start', { instanceId: this.instanceId, chars: host.length });
}
Diagnostics.log('error', 'network', 'request_failed', { code: error.code }, error);
```

Debug/Info 的高频调用在构建字段前检查 `acceptsLog`，关闭时不分配字段对象、不读错误正文、不读时钟、不做脱敏或序列化。接口本身也会检查，调用者不必承担正确性责任。Warn/Error 的异常路径保留必要的系统输出成本，不声称为零开销。日志本身失败不会替换业务异常，输出失败计数在开发者页和导出中可见。

日志结构为 `level/module/event/fields`，采集缓冲外层带 `seq/time`。系统 HiLog 使用同一份脱敏数据，并由系统日志头提供时间。日志等级 Debug / Info / Warn / Error 默认为 Info，开发者页可以切换；仅符合阈值的日志进入采集。低于阈值的 Warn/Error 仍可进入系统 HiLog。`filtered` 只统计实际进入接口的过滤调用，调用点前置门控跳过的 Debug/Info 不增加计数。

名称与字符串值使用固定目录：未知模块或事件被拒绝并计数；未知字段直接忽略；协议、阶段、动作、策略等仅保留允许的枚举，否则替换为 `[redacted]`。数值必须有限、布尔值必须类型正确。引用 ID 转为每次采集重新编号的 `ref-N`，映射容量为 512，超出容量后遮蔽。自由文本异常只提取数值错误码、允许的符号错误码和固定错误分类，异常正文与堆栈不导出。模型名、字体列表、浏览器 URL 和可任意填写的名称也不写入日志。

新增日志需要在 `DiagnosticLog.ets` 的事件目录和字段定义中登记，不应把正文拼进事件名或字段。`scripts/test-unified-logging.cjs` 会检查业务代码不再直接调用或导入 HiLog，并验证所有固定调用点均已登记。沙箱用户程序的 `console` 输出属于工具结果，不自动并入应用诊断日志。

运行日志使用独立 1000 条环形缓冲，全程等级计数独立保留，不受性能明细覆盖影响。`capture.logging` 包含记录、等级、覆盖、过滤、拒绝和输出失败计数。性能事件与运行日志在批量 JSONL、导出和 Chrome Trace 中按共享序号合并。关闭“详细事件时间线”不会关闭运行日志，日志由诊断总开关和等级独立控制。

采集只覆盖当前 App 进程；其他进程的系统日志、系统备份进程未运行中的历史日志不会自动倒灌。进入后台暂停主动资源采样，已开启的运行日志仍会随业务路径记录；停止采集后只保留系统 Warn/Error。日志等级在进程重启后恢复 Info，采集依然保持关闭。
