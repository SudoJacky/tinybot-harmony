# 多设备协同（实验）

从对话右上角菜单进入“多设备协同（实验）”。两台真机均启用协同并授权发现附近设备，然后选择连接方式：

- 鸿蒙原生协同：在任一端选择另一台可信设备连接。当前按同一华为账号、Wi-Fi 与蓝牙均已开启的场景验证；设备必须已建立系统可信关系。
- 局域网直连：两端连接同一 Wi-Fi，在一端生成连接码，复制到另一端的输入框并连接。使用鸿蒙 NetworkKit TCP 与 CryptoArchitectureKit AES-256-GCM，适用于原生握手失败时手动选择，不会自动切换方式。连接成功后明确显示当前方式。

连接码含随机密钥，5 分钟内有效，任一端都可生成。点击“断开”结束当前连接；有效期内可使用同一连接码重连。过期会关闭监听并撤销连接码，已有连接继续使用。重新生成、切换到原生方式、关闭协同或退出应用均撤销监听。每次 TCP 连接使用新的挑战值，方向与序号参与认证，未通过连接码认证不会进入会话共享。不要把连接码发给其他人。

连接后可在“本机”和对端设备页签查看各自会话列表。选择执行设备后新建会话，或选择已有会话继续发送。任务、模型调用、工具和持久化均发生在会话所属设备；另一端接收文本输出和工具状态。同会话的多端输入按执行端队列顺序处理，不改变执行端当前浏览的会话，也不读取或清空该设备的输入草稿。“停止”只停止选中的会话。关闭协同不停止已经接受的任务。

原生方式使用 `@kit.DistributedServiceKit` 的 `distributedDeviceManager` 发现可信设备，使用 `abilityConnectionManager` 建立前台协同连接、接收 `onCollaborate` 生命周期并双向通信。未启用协同时拒绝连接；原生接收端只接受同包名、同模块、同 Ability、同协议的连接。直连方式仅在用户生成连接码时监听当前网络的私有 IPv4 地址；两种方式均不增加云端中转。

原生 `sendMessage` 的 1 KB 上限由 UTF-8 分片和有序重组处理。首次选择会话发送快照，后续只发送变化的消息及新增文本。每次查看有独立标识，切换会话后丢弃旧订阅的迟到数据。连接断开时保留最后画面并明确标记状态未更新；手动重连后重新获取快照，不自动重发执行指令。接收端缓存本进程最近 512 条指令回执以去重。未收到回执时应先检查执行端会话，避免重复提交。

当前范围：

- 两台前台真机；不保证锁屏、后台和远程唤醒。模拟器不支持该系统能力。
- 文本消息、会话状态、工具名称与执行状态；附件传输、远端文件预览、远程工具确认和运行中迁移尚未实现。
- 模型服务及密钥不跨设备同步，使用执行设备已有的可用模型配置。未发送草稿、系统提示词、运行上下文和工具参数不进入协同协议。
- 远端视图只存在内存；原始会话由执行设备保存。单次快照最多 2,097,152 个 UTF-16 字符，超过时显示错误，不截断内容。
- 暂停且仍有待发指令的会话，需要先在执行设备处理原队列。新指令不会隐式恢复旧队列。

2026-11-08 已在 Mate 70 Pro+ 和 MatePad 11.5 两台真机验证：原生发现与连接、双向新建与执行、执行中持续显示新增文字、双端同时处于执行中、完整接收中文短文及 1–1000 的输出、远程停止（交互工具取消）、断开后手动重连恢复状态，以及手机键盘弹出后正常发送。新增编译产物测试覆盖消息卡从初始空内容到连续输出、完成及停止状态的实际更新回调。调试截图与 UI 树保留在本地 `.hvigor/collaboration-evidence/`。

## 已知的重连故障（2026-11-08 补充）

上面的原生重连验收仅覆盖了继续由平板发起连接，不能代表换端建链也能成功。用户报告主动断开后两端发起均失败；随后在上述两台 API 26、`OpenHarmony-7.0.0.111` 真机上反复复现其中一条失败路径：平板连接手机成功；断开后改由手机连接平板，返回 `ConnectErrorCode.SYSTEM_INTERNAL_ERROR`（5）；再次改由平板发起可以成功。此复现不足以解释用户遇到的所有情况。

系统日志显示，失败停在 `SOURCE_GET_PEER_VERSION_STATE`，发送 `SINK_GET_VERSION_CMD` 后约 10 秒超时，内部原因码 `29360340`，尚未进入对端应用的接入流程。故障现场见本地 `.hvigor/collaboration-reconnect-phone-live.log` 与 `.hvigor/collaboration-reconnect-tablet-live.log`。公开框架源码仅作机制参考，不能替代对安装版本的定位。

已做的区分实验：刷新可信设备列表、补齐 PeerInfo 的 serviceName、销毁前显式 disconnect 均未解决换端建链，后两项实验性改动已撤回。公开参考实现的 `DestroySession` 本身会调用 `Disconnect`，真机也记录到这条调用，因此不把重复调用 disconnect 当成根因修复。

保留的应用改进是：失败诊断记录原生错误码与会话代次；注销监听失败时仍继续销毁会话；系统错误 5 提示可手动选择局域网直连。这些改进通过回归与构建，但系统握手超时仍未根治。新增直连方式供继续试用，不能当成修复了原生故障。

直连验证已在同一对真机完成：平板生成连接码、手机接入，连续 3 轮手动断开重连（包含由平板断开）；重连后手机新建平板会话、发起模型请求并收到完整答复。交换角色后，手机生成连接码、平板接入并断开重连；平板新建手机会话、发起请求并收到完整答复。平板浮动键盘下的配对按钮改放到输入框下方左侧，也支持键盘提交。最终构建已重新安装，两端启动冒烟通过；输出证据位于本地 `.hvigor/collaboration-evidence/lan-phone-reconnected-output.json` 和 `lan-tablet-reconnected-output.json`。原生错误 5 的故障结论保持不变。

`test-lan-collaboration.cjs` 使用真实直连适配与协同控制器、Node AES-GCM 和可拆包的内存 Socket，覆盖认证、篡改与跨连接/方向重放拒绝、连续交替建链与原码重连、错误密钥后的恢复，以及取消尚未完成的监听时释放端口。上述脚本、原生协同回归、并行会话回归、编译后消息卡更新、日志脱敏与双语词条验证均通过；ArkTS 检查无错误，Debug 构建成功。

## 原生 API 与断开顺序复核（2026-11-08）

依据华为官方[开发指南](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/abilityconnectmanager-guidelines)与[API 参考](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-distributed-abilityconnectionmanager/)：

- 指南明确允许直接 `destroyAbilityConnectionSession`，会自动断开；短期重连也可仅 `disconnect` 并复用原 sessionId。因此旧实现直接销毁不等于遗漏了必需的断开 API。
- 对照实验曾改为：主动短期断开仅调用 disconnect，被动断开只记录状态、保留会话，同设备重连复用 ID，关闭协同等场景再销毁。真机日志确认同一应用 sessionId 100 已被复用，同端重连成功，但换端时仍原样超时。此方案未解决故障，已撤回，最终保持官方允许的直接销毁方式。
- 接收请求的 `acceptConnect` 完成不代表通道就绪。已修正为等待原生 connect 事件后才共享会话与发消息，接收早到消息也不会绕过此状态。
- 原实现拒绝请求时只返回 REJECT，未调用官方 reject 传递原因。已补齐关闭、忙碌与接入失败的明确原因，发起端优先显示这些已知原因，避免都显示错误 5。

原包对照：Wi-Fi 重连后，手机的旧 5 号系统通道被清除，新 19 号通道已完成版本握手；此时另一端应用进程重启导致未启用协同，记录到 `accept_rejected enabled=false`，系统仍映射为错误 5。重新在两端启用后，手机建链成功；手机同端断开重连也成功，但换平板发起时再次超时：平板系统调度进程复用了第一轮留下的 20 号通道，引用计数从 1 增至 2，未收到版本响应，10 秒后减回 1。故障发生在进入手机应用之前，区别于接收端开关未启用。

清除旧通道后，复用方案再次复现：手机新建系统通道 22；主动断开时手机将引用计数减至 0 并关闭；平板的系统调度进程仍保存此通道。手机同端重连使用新通道 23 且成功，改由平板发起后，平板重新选择旧 22 号通道，引用计数 1→2；10 秒后超时，再减为 1。此前由平板先连接时，相同故障发生在手机。这说明故障跟随原接收端角色，并非固定某一台设备或应用 sessionId 未销毁。双方 BluetoothHost dump 确认 Bt 与 Ble 均 enabled。

上述现象定位到系统调度进程保留的控制通道；应用会话 ID 与此通道 ID 不是同一资源。公开参考实现的 ConnectDevice 会按 peerDeviceId 复用缓存通道，CleanUpSession 在 source 分支释放控制连接，sink 侧另依赖底层 OnShutdown 维护缓存。这与日志现象相符，但不能替代对安装版本中“为何缺失回收通知”的定位，也不能把原生重连称为已修复。该参考源码固定于 OpenHarmony ability_dmsfwk 的 `bf8838bb6ad160340e950d80f26ceef0c8018bc5`。

保留改动为接收端等待 connect 事件、按连接代次忽略旧回调，以及 reject 的明确拒绝原因。真机已验证：关闭对端协同时，发起端显示“请先在另一台设备开启多设备协同。”，替代此前同样报错误 5 的情况。原生适配回归、局域网回归、日志脱敏、词条验证、ArkTS 检查与构建均通过。原包日志为本地 `.hvigor/native-audit-*-after-wifi.log`，复用方案为 `.hvigor/native-reuse-*-live.log`；旧安装包留存 `.hvigor/native-audit-baseline.hap`，SHA-256 为 `FD766D783530D00447E3944AB62A9B080E3D776EED46C1765E84A24EF5C5268D`。没有把测试失败的复用方案留在最终实现中。

最终包已重新安装到两台真机并通过启动冒烟，手机发起原生连接后，新建平板会话、执行请求、同步完整答复成功，证据为本地 `.hvigor/collaboration-evidence/native-final-phone-output.json`。结束时保留这条原生连接；已停止本次启动的日志采集进程。上述成功不代表换端重连已修复。
